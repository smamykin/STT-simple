# Реализация текущей версии

## Статус платформ

Текущая рабочая платформа — macOS. Backend и frontend TTS реализованы. Реальный платный запрос OpenAI TTS в этой macOS-сессии пока не выполнялся, поэтому end-to-end проверка Speech API остаётся пунктом ручного чек-листа.

Linux runtime для TTS реализован, включая чтение Wayland clipboard через `wl-paste`, запуск через `--toggle-tts` и воспроизведение WAV, но на Linux TTS не проверен. Исторические результаты Ubuntu 22.04 / Wayland ниже относятся к более раннему STT-состоянию проекта и не должны трактоваться как проверка TTS.

## Компоненты

- **Frontend:** React + TypeScript + Vite. Настройки и действия вызывают Rust-команды через Tauri IPC; событие `app-state` обновляет интерфейс. Во время записи снимок состояния запрашивается раз в секунду для таймера. UI содержит отдельные секции диктовки и озвучивания, TTS model/voice/hotkey и disclosure: сгенерированный голос является голосом ИИ, а не человека.
- **Desktop-бэкенд:** Tauri 2. Управляет состояниями, системным треем и горячими клавишами. Изменения состояния сериализованы; события и обновления трея доставляются на главном потоке с актуальным снимком.
- **Захват аудио:** CPAL. Stream создается и закрывается в отдельном потоке; приложение хранит только отправляемый между потоками proxy. Готовность после остановки означает, что поток подтвердил закрытие микрофона.
- **Воспроизведение:** rodio. Полученный WAV остаётся в `Vec<u8>`, декодируется через `Cursor<Vec<u8>>` и передаётся worker-потоку. Подготовка плеера происходит беззвучно, playback начинается отдельной командой. Остановка считается завершённой только после подтверждения освобождения sink/stream. Временные аудиофайлы не создаются.
- **Ядро:** отдельный crate `stt-core`, не зависящий от GUI. STT WAV — mono PCM16, 16 кГц; длительность вычисляется до ресемплинга по числу аудиокадров. Ядро содержит настройки и OpenAI-клиент для STT/TTS, полировки и каталога моделей.
- **Сеть STT:** reqwest с Rustls, фиксированный endpoint `https://api.openai.com/v1/audio/transcriptions`, multipart WAV, JSON-результат. Для Diarize отправляется `chunking_strategy=auto`, приложение использует только поле `text`. Новые настройки используют `gpt-transcribe`; явный ранее сохраненный выбор остается прежним.
- **Сеть TTS:** тот же клиент отправляет JSON на фиксированный endpoint `https://api.openai.com/v1/audio/speech`: `model`, `voice`, исходный неусечённый `input`, `response_format="wav"`. По умолчанию используются `gpt-4o-mini-tts` и `marin`. Пустой текст и ввод длиннее 4096 Unicode-символов отклоняются до сети; потоковый WAV-ответ ограничен 64 MiB.
- **Полировка и каталог:** при выбранном профиле после STT выполняется отдельный JSON-запрос в OpenAI Responses API `POST /v1/responses` с тем же ключом и `store: false`. Каталог моделей запрашивается отдельно через `GET /v1/models` только по нажатию кнопки.
- **Общие сетевые свойства:** redirects запрещены, timeout — 120 секунд, пользовательский endpoint не поддерживается. UI и Rust проверяют формат custom model/voice IDs без жёсткого allowlist; доступность и совместимость определяет OpenAI. Сырые тела ошибок пользователю не показываются.
- **Ключ:** keyring 3 — Secret Service на Linux, Keychain на macOS. Ключ отсутствует в JSON состояния/настроек; временные строки ключа в бэкенде оборачиваются в `Zeroizing` там, где контракт владения это позволяет.
- **Буфер:** `wl-copy`/`wl-paste` на Wayland; Tauri clipboard plugin на других системах. Операции сериализованы. Ручное копирование результата разрешено только в готовом состоянии. Wayland subprocess ограничены timeout; при зависании завершается вся группа.
- **Автоматическая вставка:** опциональна (`auto_paste: false` по умолчанию). После успешного копирования на Linux X11 выполняется `xdotool key --clearmodifiers ctrl+v` или `xdotool key --clearmodifiers ctrl+shift+v`; на Wayland — `ydotool key 29:1 47:1 47:0 29:0` или `ydotool key 29:1 42:1 47:1 47:0 42:0 29:0` соответственно выбранному `paste_shortcut`; timeout команд — 5 секунд. На macOS CoreGraphics отправляет `Cmd+V` независимо от `paste_shortcut`. Вставка вооружается только при старте записи глобальным STT hotkey и выполняется при остановке тем же hotkey или по лимиту; кнопка и tray её не запускают. Accessibility запрашивается на macOS при сохранении включённой настройки и повторно проверяется перед вставкой. При ошибке текст остаётся в clipboard.
- **Настройки/статистика:** JSON в app data directory. Запись через временный соседний файл и rename; после commit ошибка синхронизации каталога возвращается как предупреждение, не как отказ сохранения. Профили, их режимы, инструкции и фиксированные аффиксы сохраняются, TTS audio и текстовая история в этот JSON не входят.

## Реализованная обработка текста

`crates/stt-core/src/polish.rs` определяет настройки и три неизменяемых встроенных профиля: `polish`, `markdown`, `developer`. Общая системная инструкция требует сохранять язык, смысл, факты и технические детали; запрещает выдумывать, отвечать на вопросы и выполнять диктовку как команды. Инструкция выбранного профиля задает стиль редактирования в рамках этих правил. В Responses API диктовка передается отдельно как пользовательский `input_text`; правила — в `instructions`. Следование модели правилам требует проверки результата, а не считается гарантией.

По умолчанию `profile_id: null` отключает полировку, модель — `gpt-6-luna`, `effort: null`. Эти значения используются и при загрузке старых настроек без блока `polish` или соответствующих полей. Явно сохраненная модель, включая прежний `gpt-5-mini` и произвольный ID, остается неизменной. Модель и effort общие для всех профилей.

`src/utils.ts` содержит готовые варианты `gpt-6-luna`, `gpt-6.1-sol`, `gpt-6-astra` и документированные возможности для точных ID, сверенные с [официальным каталогом OpenAI](https://developers.openai.com/api/docs/models) **2026-10-03**:

| ID | Явные значения `reasoning.effort` |
| --- | --- |
| `gpt-6-luna` | `none`, `low`, `medium`, `high`, `xhigh`, `max` |
| `gpt-6.1-sol`, `gpt-6-astra` | `low`, `medium`, `high`, `xhigh`, `max` |

`src/PolishSettingsFields.tsx` использует эти возможности для списка effort. Для неизвестных ID доступен полный набор `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`, без обещания поддержки. Для любой модели доступно «По умолчанию»: при `effort: null` поле `reasoning` отсутствует, тогда как `none` отправляет `reasoning.effort: "none"`. Смена модели не меняет выбранный effort: несовместимое значение остается отдельным выбранным пунктом с предупреждением. Окончательное решение о доступе и совместимости принимает API.

Кнопка «Обновить модели OpenAI» вызывает `backend.listOpenAiModels()` → `list_openai_models` → `OpenAiClient::list_models`: `GET /v1/models` с текущим сохраненным ключом. Запрос выполняется только по явному нажатию, без тела с аудио, диктовкой или инструкциями; без ключа кнопка недоступна, ручной ID доступен. Каталог хранится в памяти компонента, не в настройках или истории. Все возвращенные модели доступны без фильтра по предполагаемой поддержке Responses: дополнительные ID выводятся в группе «Каталог OpenAI — совместимость не проверена», дубли готовых вариантов не повторяются. Согласно [List models](https://developers.openai.com/api/reference/resources/models/methods/list), ответ содержит базовые метаданные, не сведения о совместимости с Responses или effort.

Обновление каталога не вызывает сохранение настроек и не изменяет черновик, выбранную модель/effort или ручной ID. Во время загрузки повторный запрос заблокирован; при ошибке показывается отдельное сообщение и сохраняется предыдущий каталог. Сохраненные модели, отсутствующие в готовом или загруженном списке, остаются доступны через ручной ввод; после перезапуска выбранный ID сохраняется, сам каталог — нет. OpenAI [рекомендует Responses API для всех новых проектов](https://developers.openai.com/api/docs/guides/migrate-to-responses); это основание выбора API, а не вывод из каталога `/models`.

Встроенные профили доступны только для чтения; дублирование создает редактируемый пользовательский профиль. Пользовательский профиль содержит `mode: llm | local`, `instruction`, `prefix` и `suffix`. Отсутствующие в старом JSON поля получают `llm` и пустые аффиксы. Для `llm` обязательна непустая инструкция; для `local` — непустой после trim префикс или суффикс. Сами аффиксы не нормализуются: пробелы и переносы сохраняются буквально. Создание, изменение и удаление проходят через существующее сохранение настроек. Лимиты: 32 профиля, непустое название до 80 символов, инструкция и каждый аффикс до 8000 символов. Импорт/экспорт не реализован.

`src-tauri/src/lib.rs` выполняет STT → выбранную обработку → прежнее завершение с копированием и автоматической вставкой. `Data::accept_transcript` возвращает `TranscriptProcessing::Publish` для выключенной обработки и локального профиля либо `TranscriptProcessing::Polish` для LLM. Локальный профиль синхронно добавляет аффиксы к raw и не входит в желтую фазу; LLM-профиль добавляет их только к успешно извлеченному ответу Responses API. Фаза `polishing` блокирует новые записи, изменение настроек и ручное копирование. Автоматическая вставка сохраняет прежние ограничения: hotkey-start + hotkey-stop/лимит; запуск или остановка кнопкой/треем только копирует.

`src-tauri/src/state.rs` хранит `last_raw_transcript`, `last_transcript` и `pending_polish` только в памяти, не в `StoredData`. При успешном STT сохраняется исходный текст и очищается прежний итог; только для LLM-полировки захватывается ее конфигурация. Локальный профиль не создает задачу повтора. Ошибка полировки возвращает `idle`, сохраняя исходный текст и задачу, но не копирует, не вставляет и не публикует исходный текст как итоговый fallback.

Команда `retry_polish` доступна для неудавшейся задачи в готовом состоянии. Она загружает **текущий API key**, но использует **захваченные профиль с инструкцией и аффиксами, модель и effort**. Аффиксы добавляются после успешного ответа, поэтому ошибка или отмена оставляет raw без них. Сохранение новых настроек после ошибки, включая изменение/удаление профиля, не меняет задачу повтора. Для исправленной модели/effort нужна новая запись. Повтор вызывает только Responses API, не STT и не учет статистики; успешный итог копируется, **автоматическая вставка никогда не вызывается**. При ошибке задача остается; при успехе очищается. Если копирование успешного итога не удалось, текст доступен для ручного повторного копирования.

Старый повтор инвалидируется уже при успешном старте новой записи (`recording_started`), не только после нового STT. Отмена новой записи не восстанавливает его; ошибка запуска микрофона не сбрасывает старую задачу. При выходе исходный/итоговый текст и задача повтора теряются. Повторная обработка последнего успешного результата другим профилем — **nice to have, не реализована**; текущая команда повтора предназначена только для ошибки. Постоянной истории транскрипций нет.

LLM-полировка и каждый ее повтор — дополнительный платный текстовый запрос, раскрывающий OpenAI текст и инструкции. Локальный профиль не делает Responses-запрос, хотя предшествующий STT по-прежнему выполняется через OpenAI. `store: false` отключает сохранение Response для последующего получения, но не означает локальную обработку или гарантию отсутствия любых видов хранения у провайдера. Ограничения внешнего буфера обмена остаются прежними.

## TTS flow и взаимное исключение операций

1. `toggle_speech` принимается только в `idle`, `synthesizing` или `playing`.
2. В `idle` backend создаёт TTS session, переводит snapshot в `synthesizing`, читает и валидирует clipboard, загружает API key и запускает OpenAI synthesis.
3. После успешного ответа WAV готовится в RAM-плеере, затем состояние меняется на `playing` и начинается вывод.
4. Повторный вызов в `synthesizing` или `playing` посылает cancellation/stop и не возвращает приложение в `idle`, пока подготовка или playback не подтвердят освобождение ресурсов. Остановка плеера ограничена внутренним timeout 3 секунды; при отсутствии подтверждения новая операция блокируется с ошибкой.
5. TTS-вызов во время `recording`, `transcribing` или `polishing` игнорируется/недоступен в UI и tray.
6. STT-вызов во время TTS сначала вызывает полную остановку TTS и ждёт её завершения. Только после этого запускается обычный путь записи и открывается микрофон.

`Phase` включает `idle`, `recording`, `transcribing`, `polishing`, `synthesizing` и `playing`. Tray показывает текстовый статус и цвета: красный для готовности, зелёный для записи, синий для распознавания, жёлтый для полировки или синтеза речи и фиолетовый для воспроизведения. Его TTS action переключается между «Озвучить буфер» и «Остановить озвучивание»; STT action во время TTS подписан «Остановить озвучивание и начать запись».

## Горячие клавиши

### macOS и X11

Обе комбинации регистрируются через native global-shortcut plugin. Backend default для TTS — `Control+Super+A`; UI macOS форматирует его как `Ctrl+Cmd+A`, не изменяя сохранённое значение. STT default macOS аналогично хранится как `Control+Super+R` и показывается как `Ctrl+Cmd+R`. Настройки запрещают эквивалентные STT/TTS-комбинации.

### Ubuntu 22.04 / GNOME 42 / Wayland

Прямой global-shortcut plugin не инициализируется в Wayland-сессии. Для STT сохранение настроек через GIO/GSettings создаёт/обновляет собственную привязку `/org/gnome/settings-daemon/plugins/media-keys/custom-keybindings/stt-simple/` с именем `STT Simple`, выбранным сочетанием и абсолютным путём к бинарнику плюс `--toggle`. При запуске выполняется только read-only проверка, не регистрация.

Автоматическая GNOME-регистрация остаётся только для STT. Для TTS snapshot отдаёт отдельную команду текущего бинарника с `--toggle-tts` и сообщение о необходимости вручную назначить её в системных сочетаниях. Это применимо и к другим Wayland-окружениям.

Snapshot отдельно передаёт `hotkey_mode` (`native` или `system`), STT `hotkey_command`/статус и TTS `tts_hotkey_command`/статус. `hotkey_available` отражает native-регистрацию либо соответствие системной GNOME STT-привязки настройкам на момент запуска/сохранения. На Wayland `tts_hotkey_available` остаётся false, потому что ручную системную привязку приложение не может подтвердить.

Кнопка сохранения в системном режиме доступна даже без изменения полей, чтобы применить STT-привязку впервые или восстановить её. Чужие записи сохраняются; обнаруженные конфликты с пользовательскими и встроенными GNOME-сочетаниями блокируют сохранение STT-настройки.

Модификаторы и клавиши преобразуются в GTK accelerator; проверяются эквивалентные записи. Неподдерживаемые соответствия клавиш отклоняются. GSettings-запись выполняется вне UI-потока, проверяются доступность схем/dconf, writable и readback. При ошибке откатываются только значения, не изменённые после нашей записи; откат списка сохраняет сторонние записи. GSettings не имеет общего CAS/транзакции между путями, поэтому гонки с внешними писателями не полностью исключены. Readback не доказывает успешный захват клавиш композитором; расширения и layout-зависимые физические клавиши могут не обнаруживаться. Привязка не удаляется при выходе и может запускать приложение.

Single-instance plugin передаёт повторные вызовы работающему экземпляру. Запросы, пришедшие до завершения инициализации, ставятся в очередь. `--toggle` запускает STT, `--toggle-tts` запускает TTS; успешные фоновые действия не переводят фокус на окно.

Монитор микрофона проверяет ошибки и лимит записи каждые 500 мс. Его действие привязано к ID конкретной записи, поэтому устаревший сигнал не может остановить или начать другую запись. Лимит — 10 минут; при достижении выполняется штатная остановка и STT.

Трей требует работающей AppIndicator-интеграции. На Linux окно при закрытии сворачивается вместо полного скрытия, поскольку tray-объект не доказывает фактическую видимость значка.

`wl-copy` может использовать временный файл и сохранять владение буфером после выхода приложения. Clipboard в целом не является приватным хранилищем: системные менеджеры истории и другие приложения могут сохранять текст. Нельзя обещать, что скопированный текст никогда не попадёт на диск или исчезнет после выхода.

## Приватность и стоимость

- STT отправляет в OpenAI аудио, модель и API key.
- TTS отправляет в OpenAI clipboard text, модель, голос и API key.
- Использование API оплачивается аккаунтом OpenAI пользователя. Приложение не показывает и не утверждает конкретную цену.
- STT audio до отправки и TTS WAV response/playback находятся в RAM. STT Simple не создаёт temp audio files и не ведёт постоянную историю аудио, транскрипций или TTS.
- На диск сохраняются настройки без ключа и агрегированная статистика записей. API key хранится в системном хранилище секретов.

## Зависимости и ограничения автоматической вставки Linux

UI показывает настройку на Linux и macOS; для Linux пояснение выбирается по `systemHotkey` (`hotkey_mode === 'system'` означает Wayland), а не по наличию X11 в user agent. На неподдерживаемых платформах настройка скрыта. Поле `Settings.paste_shortcut` присутствует на всех платформах и сериализуется как `ctrl_v` (по умолчанию, в том числе при загрузке старых настроек без поля) или `ctrl_shift_v`. Селектор «Сочетание для вставки» виден только на Linux, отключён при `auto_paste: false` и наследует блокировку fieldset во время записи, обработки и выполнения команды. Draft, нормализация, сравнение настроек и сохранение сохраняют поле и на других платформах. UI не отправляет клавиши самостоятельно: выбор сохраняется через существующие настройки, а eligibility сессии и вставку обеспечивает бэкенд.

На X11 нужен `xdotool` в `PATH`. На Wayland нужен `ydotool`; современный ydotool 1.x требует отдельно настроенного пользователем демона `ydotoold`, доступа к `/dev/uinput` и сокету. Приложение наследует `YDOTOOL_SOCKET`; значение должно присутствовать в окружении при запуске, в том числе через GNOME. Пакет `ydotool` из apt Ubuntu 22.04 может быть legacy, поэтому установка пакета сама по себе не гарантирует современную 1.x и рабочую вставку. Настройка демона/службы и прав зависит от дистрибутива и версии пакета; универсальные инструкции service setup неприменимы. Приложение не выполняет sudo и не меняет службы или права автоматически. Не следует давать всем пользователям права записи в uinput или сокет. См. [README](../README.md#linux).

На Linux отправляется одно выбранное сочетание: `Ctrl+V` или `Ctrl+Shift+V`. Выбор глобален, без определения приложения и без попытки второго сочетания после первого. Пользователь выбирает сочетание, работающее вручную в целевом поле; `Ctrl+Shift+V` может подходить для обычного текста в чате Zed или терминала, но не является универсальным требованием Zed. Цель — поле с фокусом на момент завершения распознавания и опциональной полировки, исходное окно не сохраняется и не активируется. Успешный exit команды не доказывает принятие ввода. Ошибка или тайм-аут вставки не удаляет текст из буфера.

## Статистика

Последняя длительность, сумма длительностей и количество непустых записей сохраняются между запусками. Учитываются завершенные и отмененные записи, независимо от успеха OpenAI. Сброс выполняется только в готовом состоянии. Статистика не хранит тексты или аудио и не учитывает TTS.

Денежная стоимость не показывается и не оценивается ни для STT, ни для TTS.

## Границы проверки

Frontend unit/component tests и Rust unit tests не доказывают работу микрофона, native/Wayland hotkey, системного хранилища, clipboard, трея, реального OpenAI Speech API, устройства вывода или синтетического `Cmd+V`/`Ctrl+V`/`Ctrl+Shift+V` через xdotool/ydotool. Эти возможности проверяются в настоящем desktop-сеансе. macOS не считается полностью проверенной до выполнения сценария автоматической вставки в стороннем приложении.

Строгая совместимость проекта с Rust 1.77.2 не заявляется: несмотря на `rust-version` в manifests, текущий lockfile включает зависимости, которым нужен более новый toolchain и Edition 2024. Для сборки используйте актуальный совместимый Rust stable.

## Отмена диктовки и обработки

Пункт отмены в трее активен в `recording`, `transcribing` и `polishing`; подпись меняется по этапу. Отмена записи завершает захват и учитывает длительность без отправки аудио. Распознавание и полировка, включая повторную, получают отдельный идентификатор операции и watch-канал отмены. Отмена прерывает ожидание HTTP-запроса, а завершение под `Runtime.control` проверяет идентификатор и сигнал отмены перед публикацией результата. Отменённая операция не может перезаписать новую.

Подготовка аудио после остановки записи завершается с подтверждением освобождения микрофона и учётом статистики; сигнал отмены принимается и на этом этапе, но `idle` публикуется после подготовки. Отмена распознавания не публикует текст текущей записи. Отмена полировки публикует `last_raw_transcript` как итоговый результат, копирует его в буфер, очищает задачу повтора и не выполняет автоматическую вставку. Отмена не считается ошибкой; ошибки буфера и сохранения статистики по-прежнему показываются.

Ручная проверка: отменить запись, распознавание, полировку и повторную полировку через трей; после каждой отмены начать новую диктовку и убедиться, что старый ответ не изменил результат. При отмене полировки проверить исходный текст в результате и буфере, отсутствие аффиксов и автовставки. Локальные профили на Linux runtime не проверены вручную.
